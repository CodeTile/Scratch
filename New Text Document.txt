Yes. After seeing the actual API, this is the approach I'd use. There's no need for an intermediate `TreeNode` at all.

## Grid item

```csharp
public enum GridItemType
{
    Object,
    Item
}

public sealed class MyGridItem : HierarchicalGridItem<object, MyGridItem>
{
    public required GridItemType Type { get; init; }

    public string Name =>
        Item switch
        {
            MyObject o => o.Name,
            FooBar f => f.Name,
            _ => string.Empty
        };

    public MyObject? MyObject => Item as MyObject;

    public FooBar? FooBar => Item as FooBar;
}
```

Notice that `Item` comes from the base class:

```csharp
public required object Item { get; init; }
```

so it can hold either a `MyObject` or a `FooBar`.

---

## Build the hierarchy

```csharp
private MyGridItem Build(MyObject obj, int depth = 0)
{
    var gridItem = new MyGridItem
    {
        Item = obj,
        Type = GridItemType.Object,
        Depth = depth,
        IsCollapsed = true
    };

    foreach (var child in obj.Children)
    {
        gridItem.Children.Add(Build(child, depth + 1));
    }

    foreach (var item in obj.Items)
    {
        gridItem.Children.Add(new MyGridItem
        {
            Item = item,
            Type = GridItemType.Item,
            Depth = depth + 1
        });
    }

    return gridItem;
}
```

Then:

```csharp
private List<MyGridItem> GridItems = [];

protected override void OnInitialized()
{
    GridItems = RootObjects
        .Select(Build)
        .ToList();
}
```

## Why I like this design

You don't have three models (`MyObject`, `TreeNode`, `MyGridItem`). You have just:

* `MyObject` (your domain model)
* `FooBar` (your domain model)
* `MyGridItem` (your UI model)

The grid item is responsible for:

* hierarchy (`Children`, `Depth`, `IsCollapsed`)
* exposing display properties (`Name`, `Type`)
* carrying the underlying object (`Item`)

## An even cleaner version

Since every row has a `Name`, you can avoid the `switch` expression by introducing a tiny interface:

```csharp
public interface ITreeItem
{
    string Name { get; }
}
```

Then:

```csharp
public class MyObject : ITreeItem
{
    public string Name { get; set; } = "";
    public List<MyObject> Children { get; set; } = [];
    public List<FooBar> Items { get; set; } = [];
}

public class FooBar : ITreeItem
{
    public string Name { get; set; } = "";
}
```

Now your grid item becomes:

```csharp
public sealed class MyGridItem : HierarchicalGridItem<ITreeItem, MyGridItem>
{
    public required GridItemType Type { get; init; }

    public string Name => Item.Name;
}
```

No casting, no `switch`, no duplicated `Name` property logic. You still have access to the original types when needed:

```csharp
if (gridItem.Item is MyObject obj)
{
    // ...
}

if (gridItem.Item is FooBar foo)
{
    // ...
}
```

For this API, that's the design I'd recommend because it's simple, type-safe, and keeps your UI model very lightweight.

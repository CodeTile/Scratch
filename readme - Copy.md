============================================================
.NET 10 BLAZOR + FLUENT UI V5
WINDOWS ACTIVE DIRECTORY AUTHENTICATION
IIS PRODUCTION SETUP
============================================================

PURPOSE
=======

Build a .NET 10 Blazor Web App using:

    .NET 10
    Blazor Web App
    Interactive Server
    Fluent UI Blazor v5
    Windows Authentication
    Active Directory
    IIS for production

The application should:

    1. Automatically authenticate users using their Windows account.
    2. Display the logged-in user's identity.
    3. Display their:
       - Display name
       - Logon name
       - Email address
       - Active Directory groups
       - Claims
    4. Allow pages to be protected using AD group membership.
    5. Allow Fluent UI controls to be shown based on authorization.
    6. Keep actual authorization enforced on the server.
    7. Be suitable for deployment to IIS.


============================================================
1. ARCHITECTURE
============================================================

The application will use this architecture:

    Browser
       |
       | Windows Authentication
       v
    IIS
       |
       | Authenticated Windows Identity
       v
    ASP.NET Core / .NET 10
       |
       +------------------------+
       |                        |
       v                        v
    ClaimsPrincipal       Active Directory
       |                        |
       |                        |
       +-----------+------------+
                   |
                   v
             UserContextService
                   |
                   v
             Blazor / Fluent UI


IIS is responsible for authenticating the Windows user.

ASP.NET Core is responsible for authorization.

Fluent UI is responsible only for the user interface.

Do NOT use Fluent UI or client-side code as the security
boundary.

    cd MyAdApp

============================================================

Install Fluent UI:

    dotnet add package Microsoft.FluentUI.AspNetCore.Components

    dotnet restore


============================================================
4. CONFIGURE PROGRAM.CS
============================================================

Program.cs should contain the following general structure:

    using Microsoft.AspNetCore.Server.IISIntegration;
    using Microsoft.FluentUI.AspNetCore.Components;

    var builder = WebApplication.CreateBuilder(args);

    builder.Services.AddRazorComponents()
        .AddInteractiveServerComponents();

    builder.Services.AddFluentUIComponents();

    builder.Services.AddAuthentication(
        IISDefaults.AuthenticationScheme);

    builder.Services.AddAuthorization();

    // Application services will be registered here.

    var app = builder.Build();

    app.UseAuthentication();
    app.UseAuthorization();

    app.MapRazorComponents<App>()
        .AddInteractiveServerRenderMode();

    app.Run();


IMPORTANT:

The authentication configuration should match the hosting
configuration generated by the .NET project.

If the project template has already configured Windows
Authentication, do not duplicate authentication registrations.


============================================================
5. CONFIGURE IIS
============================================================

In IIS Manager:

    Sites
       -> MyAdApp
          -> Authentication


Set:

    Windows Authentication       ENABLED
    Anonymous Authentication     DISABLED


The application should NOT use a normal username/password
login page.

The Windows account should be supplied automatically by IIS.


============================================================
6. IIS WINDOWS AUTHENTICATION
============================================================

Windows Authentication can use:

    Kerberos
    NTLM

In an Active Directory environment, Kerberos should normally
be preferred where the IIS/server configuration supports it.

Do not attempt to implement your own Kerberos or NTLM handling
inside the Blazor application.

IIS handles the Windows authentication handshake.


============================================================
7. IIS APPLICATION POOL
============================================================

Create a dedicated IIS Application Pool for the application.

Example:

    MyAdAppPool


Use:

    No Managed Code


The application is ASP.NET Core and is not an old ASP.NET
Framework application.

Decide deliberately what identity the Application Pool should
run under.

Possible configurations include:

    ApplicationPoolIdentity

or:

    A dedicated domain service account


If the application needs to query Active Directory using LDAP,
the permissions and identity used for that lookup must be
considered separately.


============================================================
8. TEST WINDOWS AUTHENTICATION FIRST
============================================================

Before implementing AD lookups or authorization, prove that
Windows Authentication works.

Create:

    Components/Pages/Identity.razor


Example:

    @page "/identity"

    @using System.Security.Claims
    @inject AuthenticationStateProvider AuthenticationStateProvider

    <PageTitle>Identity</PageTitle>

    <h1>Windows Identity</h1>

    @if (_user == null)
    {
        <p>Loading...</p>
    }
    else
    {
        <p>
            <strong>Authenticated:</strong>
            @_user.Identity?.IsAuthenticated
        </p>

        <p>
            <strong>Name:</strong>
            @_user.Identity?.Name
        </p>

        <p>
            <strong>Authentication type:</strong>
            @_user.Identity?.AuthenticationType
        </p>
    }

    @code
    {
        private ClaimsPrincipal? _user;

        protected override async Task OnInitializedAsync()
        {
            var authenticationState =
                await AuthenticationStateProvider
                    .GetAuthenticationStateAsync();

            _user = authenticationState.User;
        }
    }


Browse to:

    /identity


Expected result:

    Authenticated: True

    Name:
        MYDOMAIN\username

The exact authentication type may vary.

9. UNDERSTAND CLAIMS
============================================================

The authenticated user is represented by:

    ClaimsPrincipal


Inspect claims with:

    user.Claims


Create a temporary diagnostic page that displays every claim.

Example:

    @foreach (var claim in _user.Claims)
    {
        <p>
            <strong>@claim.Type</strong>

            @claim.Value
        </p>
    }

Do not assume what claims are present.

Inspect the actual claims supplied by your Windows Authentication

11. WINDOWS LOGON NAME
============================================================

The Windows logon name is normally available using:

    user.Identity?.Name


Example:

    MYDOMAIN\jsmith


This is the Windows/domain identity of the authenticated user.


============================================================
12. DISPLAY NAME AND EMAIL
============================================================

Do NOT assume these values are automatically available as
claims.

You may find:

    ClaimTypes.Name

and:

    ClaimTypes.Email


For example:

    var name =
        user.FindFirst(ClaimTypes.Name)?.Value;

    var email =
        user.FindFirst(ClaimTypes.Email)?.Value;


However, if Email is null, this does NOT mean that the user
does not have an email address in Active Directory.

It means that the email address was not supplied as a claim.


============================================================
13. ACTIVE DIRECTORY LOOKUP
============================================================

If the application needs reliable AD information such as:

    displayName
    mail
    userPrincipalName
    sAMAccountName
    department
    title
    group membership


then implement a server-side Active Directory lookup.

Do NOT perform LDAP queries directly from a Razor component.


Use a service:

    ActiveDirectoryService


The architecture should be:

    Razor Component
           |
           v
    UserContextService
           |
           v
    ActiveDirectoryService
           |
           v
    Active Directory

14. USER CONTEXT MODEL
============================================================

Create:

    Models/UserContext.cs

    public sealed class UserContext
    {
        public bool IsAuthenticated { get; init; }

        public string? LogonName { get; init; }

        public string? JobTitle { get; init; }

        public IReadOnlyList<string> Groups { get; init; }
            = [];

        public IReadOnlyList<UserClaim> Claims { get; init; }
            = [];
    }

15. USER CLAIM MODEL
============================================================

Create:

    Models/UserClaim.cs


Example:

    public sealed class UserClaim
    {
        public string Type { get; init; } = string.Empty;

        public string Value { get; init; } = string.Empty;
    }


============================================================
16. USER CONTEXT SERVICE
============================================================

Create:

    Services/IUserContextService.cs


Example:

    public interface IUserContextService
    {
        Task<UserContext> GetCurrentUserAsync();
    }


Create:

    Services/UserContextService.cs


This service should:

    1. Obtain the current ClaimsPrincipal.
    2. Determine the Windows logon name.
    3. Read available claims.
    4. Look up AD information if required.
    5. Return a UserContext object.


The Razor components should use this service rather than
implementing authentication logic themselves.

============================================================

============================================================
19. ACTIVE DIRECTORY GROUPS
============================================================

There are two common ways group membership may appear.

1. Windows group membership / WindowsIdentity

2. Group SID claims


For WindowsIdentity:

    var identity =
        user.Identity as WindowsIdentity;


Then:

    identity.Groups


Groups may initially appear as SIDs:

    S-1-5-21-...


These can sometimes be translated:

    sid.Translate(typeof(NTAccount))


Result:

    MYDOMAIN\Application Administrators


Do not assume this will always be available or sufficient for
your application's AD requirements.


============================================================
20. AD GROUPS THROUGH LDAP
============================================================

For an application that needs authoritative AD group information,
consider querying Active Directory.

Typical information:

    cn
    displayName
    mail
    userPrincipalName
    sAMAccountName
    memberOf


Nested group membership may require additional processing.

Decide whether your application requires:

    Direct groups only

or:

    Effective membership including nested groups


This is important for authorization.

============================================================
24. AUTHORIZATION
============================================================

Authentication answers:

    "Who is this user?"


Authorization answers:

    "Is this user allowed to do this?"


Keep these concepts separate.


============================================================
25. CREATE AUTHORIZATION POLICIES
============================================================

Policies should be defined centrally in Program.cs.

Example:

    builder.Services.AddAuthorization(options =>
    {
        options.AddPolicy(
            "ApplicationAdmin",
            policy =>
            {
                policy.RequireClaim(
                    ClaimTypes.GroupSid,
                    "S-1-5-21-...");
            });
    });


The SID must be the actual SID of your AD group.

Do not copy an example SID into production.


============================================================
26. USING AD GROUP NAMES
============================================================

If your Windows identity exposes AD groups as roles, you may
be able to use:

    policy.RequireRole(
        @"MYDOMAIN\Application Administrators");


However, first verify:

    user.IsInRole(
        @"MYDOMAIN\Application Administrators")


and inspect the actual claims.

Do not assume that an AD group automatically becomes an ASP.NET
Core role in every configuration.


============================================================
27. PREFER STABLE AUTHORIZATION IDENTIFIERS
============================================================

Where appropriate, use the AD group's SID rather than its
display name.

For example:

    S-1-5-21-...


Advantages:

    - Group names can change.
    - Group display names can change.
    - SID identifies the security principal.


Keep authorization configuration centralized.


============================================================
28. PROTECT A PAGE
============================================================

Example:

    @page "/admin"

    @attribute [Authorize(
        Policy = "ApplicationAdmin")]


The page should only be accessible to users satisfying the
policy.


============================================================
29. PROTECT UI WITH AUTHORIZEVIEW
============================================================

Example:

    <AuthorizeView Policy="ApplicationAdmin">

        <Authorized>

            <FluentButton>
                Administration
            </FluentButton>

        </Authorized>

        <NotAuthorized>

            <p>
                You do not have access to administration.
            </p>

        </NotAuthorized>

    </AuthorizeView>


IMPORTANT:

AuthorizeView only controls what the user sees.

It is NOT the security boundary.


============================================================
30. PROTECT SERVER OPERATIONS
============================================================

Every sensitive operation must also enforce authorization.

Do NOT rely on:

    Hidden buttons
    Disabled buttons
    JavaScript
    Local storage
    Query strings
    Client-side variables


for security.


The server must verify authorization before performing a
sensitive operation.


============================================================
31. EXAMPLE POLICY STRUCTURE
============================================================

A real application might eventually have policies such as:

    ApplicationUser
    ApplicationAdmin
    ReportsUser
    FinanceUser
    ITSupport


For example:

    builder.Services.AddAuthorization(options =>
    {
        options.AddPolicy(
            "ApplicationAdmin",
            policy =>
            {
                policy.RequireClaim(
                    ClaimTypes.GroupSid,
                    ApplicationAdminSid);
            });

        options.AddPolicy(
            "ReportsUser",
            policy =>
            {
                policy.RequireClaim(
                    ClaimTypes.GroupSid,
                    ReportsUserSid);
            });
    });


Keep these definitions in one place.


============================================================
32. DO NOT PUT AD LOGIC IN EVERY COMPONENT
============================================================

Avoid this:

    Home.razor
        -> LDAP

    Admin.razor
        -> LDAP

    Reports.razor
        -> LDAP

    Settings.razor
        -> LDAP


Instead:

    Home.razor
         |
    Admin.razor
         |
    Reports.razor
         |
         v
    UserContextService
         |
         v
    ActiveDirectoryService
         |
         v
    Active Directory


This keeps the application maintainable.


============================================================
33. SECURITY OF THE DIAGNOSTIC CLAIMS PAGE
============================================================

During development it is useful to have:

    /claims

and:

    /identity


However, do not leave a page exposing all claims and AD
information publicly accessible in production.

At minimum:

    @attribute [Authorize]


Preferably restrict it to an administrator-only policy.


============================================================
34. PRODUCTION IIS CONFIGURATION
============================================================

Production IIS should have:

    Windows Authentication       Enabled
    Anonymous Authentication     Disabled


Application Pool:

    No Managed Code


Use a dedicated Application Pool.

Use HTTPS.

Use a valid server certificate.

Do not expose the application over plain HTTP in production.


============================================================
35. IIS HTTPS
============================================================

Configure an HTTPS binding in IIS.

Example:

    https://myapp.mycompany.local


Users should access the application using HTTPS.

Do not rely on HTTP simply because Windows Authentication is
being used.


============================================================
36. KERBEROS / SPNs
============================================================

If Kerberos is required in your environment, the IIS hostname,
service account, SPN and Active Directory configuration must
be correct.

For example:

    HTTP/myapp.mycompany.local


SPN configuration is an infrastructure/Active Directory
administrator task.

Do not create arbitrary SPNs without coordinating with the
AD/IIS administrators.


============================================================
37. IIS SERVER DOMAIN MEMBERSHIP
============================================================

The IIS server should normally be appropriately joined/configured
for the Active Directory environment in which Windows
Authentication is being used.

Confirm:

    Server can communicate with domain controllers.
    DNS is correctly configured.
    Domain trust is functioning.
    Users can authenticate.


============================================================
38. ACTIVE DIRECTORY SERVICE ACCOUNT
============================================================

If the application performs LDAP queries, determine whether
the application should use:

    ApplicationPoolIdentity

or:

    Dedicated domain service account


Do not automatically give the application a highly privileged
domain account.

Use the minimum permissions required.

For read-only user/group lookups, use an appropriately restricted
identity.


============================================================
39. ACTIVE DIRECTORY READ PERMISSIONS
============================================================

The application should only receive the permissions necessary
to read the required AD information.

Do not grant:

    Domain Administrator

or other highly privileged rights merely to perform user lookups.


============================================================
40. CACHING
============================================================

AD lookups do not necessarily need to happen for every UI
operation.

Consider caching the user's AD information for an appropriate
period.

For example:

    User logs in
         |
         v
    UserContextService
         |
         v
    AD lookup
         |
         v
    Cached UserContext


The cache duration depends on how quickly changes in group
membership must take effect.

Be careful when caching authorization-related information.

If immediate removal from an AD group must revoke access,
do not use a long-lived authorization cache.


============================================================
41. IMPORTANT AUTHORIZATION RULE
============================================================

Do not make authorization decisions based solely on information
retrieved from the browser.

Always use the authenticated server-side identity.

============================================================
49. LOGGING
============================================================

Add useful server-side logging around:

    Authentication failures
    AD lookup failures
    Authorization failures
    LDAP connectivity problems


Do not log:

    Passwords
    Authentication tokens
    Sensitive personal information unnecessarily
    Full claim collections in production


During development, full claims may be useful for diagnosis,
but avoid doing this in production logs.

     v

     |
     | ClaimsPrincipal
     v

============================================================
56. IMPORTANT
============================================================

The exact implementation of Active Directory lookup depends
on your environment.

Before writing the final LDAP implementation, determine:

    1. Active Directory domain name.

    2. Whether the IIS server is domain joined.

    3. Whether the application will run under
       ApplicationPoolIdentity or a domain service account.

    4. Whether group membership must include nested groups.

    5. Whether users can belong to multiple AD domains.

    6. Which AD attributes are required.

    7. Which AD groups should control application access.

Do not guess these values.
